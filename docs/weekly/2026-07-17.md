###  介绍项目
我这个项目它解决的问题就是当普通用户面对法律问题时怎样去描述案情查找相关的法律根据还有采取下一步行动的问题。

### 遇到的最大问题

我遇到的核心难点是：**如何让 RAG 评测结果可复现、可信**

参考回答：
项目中最难的部分是**建立可信的 RAG 评测**。初期我发现同类测试的*命中率波动很大*，一开始误以为是电脑性能或模型下载不完整导致的。后来我意识到，RAG 的结果不只是**向量相似度，还受向量库版本、文档切分、召回数量、Reranker 是否成功加载以及异常降级策略影响**。

## 0718

#### 如果 Reranker、Ollama 或大模型 API 挂了，系统会怎样？

当前实现：

Reranker 失败：会回退到 FAISS 原始结果。这是当前唯一明确做了**降级处理**的组件。
Ollama Embedding 服务失败：legal_rag_search 当前没有完整的异常兜底，检索工具很可能失败，进而影响整次请求。
GLM API 失败：当前也没有统一的超时、重试、SSE 错误事件处理，请求可能直接失败。
DuckDuckGo 搜索失败：这个其实你已经处理了，web_legal_search 的 except 会返回“搜索失败：…”的文本。

未来上线改进：

Ollama 不可用：明确提示**法律检索服务暂不可用，请稍后重试**，不要让模型编造。
GLM API 不可用：前端显示**请求失败和重试入口**；后端加超时、有限重试、错误日志。
Reranker 不可用：继续 FAISS 降级，但记录降级次数。
联网搜索失败：**提示“未获取到最新外部信息”**，可继续用本地库回答，但不能声称信息最新。
你现在可以这样答：
当前我只对 Reranker 做了 FAISS 降级处理。Ollama 和 GLM API 的失败处理还不完善，这是我后续优先补的工程能力；DuckDuckGo 搜索已有异常提示。上线时我会把不同组件的失败状态明确展示给用户，而不是让系统假装正常。

这个字典在 Python 程序的内存里。

Python 进程重新启动；

之前的对话和案情摘要就没了。

当前使用**内存字典**，*服务重启会丢失数据*，也不适合多实例部署。后续会通过**用户认证获得 user_id**，并将*会话和案情摘要*存入持久化数据库；Redis 可以用于短期缓存，但数据库才是长期数据来源。


#### 为什么要用 SSE 流式输出？

LLM**调用工具和生成回答的时间耗时不稳定**。SSE**允许服务端生成一部分内容后**立刻推送给前端，用户不用等待整段答案都生成后才能得到反馈。用于**改善首段响应时间和等待体验**
#### 法律助手答错、引用过期法律、泄露用户案情，怎么处理？

第一，法律来源优先使用**权威网站和本地确认过的法律文本**，并**展示来源、条款和生效时间。**
第二，*证据不足或检索失败*时，明确**提示用户核实，而不是给出确定结论**。
第三，**构建评测集**，检查引用是否正确、是否使用过期法律、*高风险问题是否被正确拒答或提示人工咨询*。
第四，隐私方面要最小化收集用户案情，**避免在日志中保存完整敏感信息**，并*评估第三方模型 API 的数据处理条款*；本地模型是一种选择，但不是唯一方案。
第五，涉及重大财产、人身或刑事风险时，**建议用户咨询专业律师**。

我认为最大不足是**评测只集中在检索来源命中**，**不能充分证明最终回答的准确性、引用完整性和法律时效性**。

## 异步处理
外部 I/O”就是程序需要**从自己当前 Python 进程外面拿数据或发数据**，于是只能等待的事情。它不只指互联网。
await会先暂停当前请求对应的协程,把执行权交回给事件循环.事件循环先去完成其他已经准备好的请求或任务,等异步操作完成后,再恢复当前协程,从await后面开始执行

我使用异步主要是**为了处理等待外部服务返回的 I/O 场景**，比如等待大模型 API、联网搜索和 SSE 推送时，不阻塞 FastAPI 继续处理其他连接。但 reranker 的 CPU 推理和同步 FAISS 查询仍然会占用当前 worker，异步不会让这类计算自动变快。我的项目当前主要用异步改善 API 等待和流式响应体验，CPU 重排序的并发优化属于后续可以继续做的方向。

我当前主要通过RAG和来源约束降低模型幻觉。优先使用本地法律文档库，然后将来源和原文片段交给模型。通过system prompt提示LLM要求基于检索结果回答。当检索的资料不足时，要提示用户注意核实，而不是给出确切答案。然后双层记忆机制用于保持多轮对话中的连续性，避免模型遗漏前文。同时提示用户对于重大财产，刑事风险，人身的案件要去咨询专业律师。

### rag流程

分为离线建库和在线检索两个阶段。

离线阶段先用PDFPlumberLoader用来加载文档,然后用rescusiveCharacterTextSplitter切分文本块,然后再用nomic-embed-text将文本块转换成向量,然后再将信息来源一起保存到FAISS向量索引。

在线阶段,用户的问题也会转化成向量。然后在FAISS中粗召回二十个候选文本块，再用BGE ranker base取前五条作为上下文和来源交给LLM生成回答。

### harness  沙箱机制
沙箱就是**安全执行环境**。AI 生成的 Shell 命令默认跑在沙箱里，**文件系统访问、网络访问、进程权限**都是受限的。就算模型输出了一个危险命令比如 rm -rf /，沙箱也会拦截，不会真的执行到我的系统上。

只有明确标记 dangerouslyDisableSandbox 且用户确认之后，命令才会在沙箱外执行。这是一个纵深防御的设计。



Agent = Model + Harness
模型只负责"想"，Harness 负责让模型"做对事、不跑偏"。

它是继 Prompt Engineering（2022-2024）→ Context Engineering（2025）→ Harness Engineering（2026） 之后的第三代 AI 工程范式。核心思想是 OpenAI 那句话："Human Steer, Agent Execute"（人类掌舵，智能体执行）。


Harness 就是模型外面那层**工程化运行框架**。模型本身只会生成文本，但实际应用中它需要**调工具、管上下文、遵守权限、被验证被纠错**——这些全是 Harness 做的事。
比如我的 legal agent 项目，LangGraph 的状态图编排（Planner → LLM ⇄ Tools）就是一层 Harness。它管了三件事：

上下文管理 — 案情摘要累积、多轮对话记忆
工具调用编排 — 让 LLM 自己去调 RAG 搜索和联网搜索
流式输出控制 — SSE 逐 token 推到前端
如果没有这层 Harness，模型只能单次问答，做不到多轮案情收集+工具检索+流式回答。


### 一、已有的 Harness 成分

| 项目实现 | Harness 七层 | 做了什么 |
|----------|-------------|---------|
| `agent/legal_agent.py` — LangGraph StateGraph | 生命周期与编排 | Planner → LLM ⇄ Tools 状态流转，控制 Agent 执行流程 |
| `case_summary` 累积存储 | 上下文管理 | 多轮对话中记住案情摘要，跨轮不丢失关键信息 |

| `SYSTEM_PROMPT` 约束"先调 RAG 再回答" | 治理 | 约束模型行为，禁止凭记忆直接回答，强制走检索链路 |
| `main.py` FastAPI 路由 | 工具接口与协议 | 把 Agent 能力暴露成 HTTP 接口，解耦前后端 |

### skills

Skills = 把"怎么做一个任务"打包成**可复用的模块文件夹**，里面有指令（SKILL.md）、脚本（scripts/）、参考文档（references/）。

核心设计：**三级渐进式披露**

这就是 Skills 最精妙的地方——**不把所有信息一次性塞进上下文，而是按需加载**：

层级        内容                  加载时机            Token 消耗
────────────────────────────────────────────────────────────
元数据层    name + description   启动时全部加载       极低（几十）
指令层      SKILL.md 正文        语义匹配命中后加载    < 5k
资源层      references/脚本      条件触发时才加载      按需



### RAG 怎么保证用户问题匹配到知识

回答要分**事前优化、事中召回、事后验证**三层。

"保证匹配分三层：**查询侧优化、检索侧多路召回、精排侧 Rerank**。核心逻辑是——召回阶段宁可多捞不漏（保 Recall），精排阶段再精选压缩（保 Precision）。"

第一层：Query 侧优化**用户问题进来先加工**

手段	做什么	举例
Query Rewrite	**补全上下文、去口语化**	"那这个怎么赔？"→"网购假货应该怎么索赔？"
Query Expansion	**加相关术语**	"工伤赔偿"→ 补充"工伤保险条例、伤残等级、误工费"
Multi Query	**拆成多个子问题分别检索**	复杂问题拆成 2-3 个子查询
HyDE	**让 LLM 先写"假设答案"，用答案去检索**	适合解释型问题，不适合精确事实

第二层：**混合召回（Hybrid Search）**
"单靠向量召回不够，**因为向量对精确词、编号、专有名词不敏感**。生产环境一般是**向量召回 + BM25 关键词召回双路并行**，然后用 **RRF（倒数排名融合）**合并——不看分数只看排名，简单稳定。"

第三层：**Rerank 精排**
"召回捞回来 20条候选，用 CrossEncoder 重排序模型逐对打分，取 Top 5 喂给 LLM。这步把 Precision 提上来，同时控制上下文长度。"


"我的项目就是这样做的：召回阶段 FAISS 向量检索取 Top 20 → CrossEncoder Reranker 重排取 Top 5 → 交给 GLM-4.7 整合回答。另外系统提示里**强制模型先调 RAG 再回答**，不凭记忆直接答——这是在 Prompt 层面兜底。
