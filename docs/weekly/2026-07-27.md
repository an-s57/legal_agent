# 2026-07-27 复盘

> 本周主题：把一个“能跑的法律 Agent Demo”，继续推进为“能测、能解释、能复现”的 RAG 应用。

## 本周完成

### 1. 改善了真实使用时的等待体验

- 为问候语等简单输入增加了快速回复路径，避免不必要地进入 Planner、检索和案情摘要更新；
- SSE 前端在收到 `done` 或错误事件后停止加载状态，避免答案已显示但页面仍持续显示“三个点”；
- 将案情摘要更新放到回答返回后进行，减少用户等待最终答案的时间；
- 通过分阶段性能日志观察请求链路，包括 Planner、LLM、向量检索、Reranker、工具调用、最终回答和后台摘要更新。

这次排查的一个重要收获是：页面“慢”不等于前端慢。一次完整法律咨询可能串行经历 Planner、模型工具决策、联网/本地检索、Reranker、最终回答等多个阶段；日志让性能问题从“感觉很慢”变成了可以定位的具体阶段。

### 2. 完成 SQLite 会话持久化

- 建立 `sessions` 和 `messages` 两张表；
- `sessions` 保存会话 ID、案情摘要和更新时间，`messages` 保存每轮用户/助手消息；
- 通过 `session_id` 将一场对话中的多条消息关联起来；
- 服务重启后，可以从 SQLite 读取历史对话和案情摘要，再注入 Agent 作为上下文。

SQLite 适合当前单机、低并发的项目阶段：不需要额外部署数据库服务，但已经把“会话只存在 Python 内存、重启即丢失”的问题解决了。以后若需要多实例部署、更高并发和共享访问，再考虑 PostgreSQL。

### 3. 建立并完成 RAG 检索参数评测

本轮评测使用 50 道人工标注的用户式法律检索题：

- 开发集 33 题：用于选择 FAISS 粗召回数量 `K` 和最终返回数量 `Top-K`；
- 验证集 17 题：用于确认选定配置；
- 每题标注目标法律来源、PDF 页码和关键证据片段；
- 主要观察来源命中率、严格证据命中率、Reranker 回退和各阶段耗时。

固定 `Top-K=5` 时，开发集的关键结果如下：

| K | 严格证据命中率 | 结论 |
| ---: | ---: | --- |
| 20 | 23/33（69.7%） | 候选不足，部分正确证据未进入重排阶段 |
| 30 | 26/33（78.8%） | 命中率提升明显 |
| 32 | 26/33（78.8%） | 没有额外提升 |
| 35 | 26/33（78.8%） | 没有额外提升 |

**K 从 20 增加到 30 时，开发集严格证据命中率从 69.7% 提升到 78.8%；继续增加到 32、35 没有额外提升，所以选择达到最佳效果的最小 K，即 30。随后在 17 道验证题上得到 15/17、88.2% 的严格证据 Hit@5。**

随后固定 `K=30` 比较 `Top-K`：

- `Top-K=3`：25/33（75.8%）；
- `Top-K=5`：26/33（78.8%）；
- `Top-K=7`：26/33（78.8%）。

因此当前线上配置为：FAISS 粗召回 **K=30**，Cross-Encoder Reranker 重排后向 LLM 提供 **Top-K=5** 条证据。选择它不是凭感觉，而是在固定语料、Embedding、切分方式和 Reranker 后，用开发集比较质量与开销得到的结果。

## 面试时可以这样总结

### 版本一：30 秒项目优化复盘

> 我先通过性能日志把端到端等待拆分为 Planner、LLM、检索、Reranker 等阶段，确认 CPU 上的 Reranker 和多次串行模型调用是主要耗时来源。之后我没有直接猜参数，而是建立了 50 道带来源、页码和证据提示的检索题集，拆分为 33 道开发集和 17 道验证集。开发集上，K 从 20 提到 30 后严格证据命中率从 69.7% 提升到 78.8%，继续增加到 32、35 没有提升，所以选择最小的最优 K=30；最终在 17 道验证题上达到 15/17、88.2% 的严格证据 Hit@5。这个过程让我把“检索效果不错”变成了可复核的数据结论。

### 版本二：被追问“你是如何定位问题的？”

> 我先给每次请求加 trace ID，并记录 Planner、LLM、工具、向量检索、重排序、最终回答和摘要更新的耗时。日志显示向量检索通常较快，而 CPU Reranker 和多次远程 LLM 调用占据主要等待时间。对于检索质量，我使用固定题集、固定语料和固定其他参数，只改变 K 或 Top-K，分别记录来源命中、严格证据命中、回退状态和耗时，再用独立的 17 道验证题确认结果。

### 术语边界

- **严格证据 Hit@5 = 88.2%** 只表示正确来源、页码和关键片段出现在最终返回的前 5 条证据中；
- 它不等于“最终法律回答 88.2% 正确”，也不能证明法律建议在真实案件中一定适用；
- 这样说明限制，比直接把它说成“模型准确率”更严谨。

## 本周反思

这周最重要的不是多加了一个功能，而是形成了一条工程闭环：

> 发现真实问题 → 加可观测日志 → 根据数据定位瓶颈 → 建立可复现评测 → 选择参数 → 用验证集确认 → 写清结论和局限。

以后每次改动都应该尽量沿着这个闭环进行，而不是只看“页面能不能跑”。
