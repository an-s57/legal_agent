### 2. 完成 SQLite 会话持久化

- **建立 `sessions` 和 `messages` 两张表**；
- `sessions` 保存**会话 ID、案情摘要和更新时间**，`messages` 保存**每轮用户/助手消息**；
- 通过 `session_id` 将一场对话中的**多条消息关联起来**；
- **服务重启后，可以从 SQLite 读取历史对话和案情摘要，再注入 Agent 作为上下文。**

SQLite 适合当前**单机、低并发的项目阶段**：**不需要额外部署数据库服务**，但已经把“会话只存在 Python 内存、重启即丢失”的问题解决了。以后若需要**多实例部署、更高并发和共享访问**，再考虑 PostgreSQL。

- **开发集 33 题**：用于选择 FAISS 粗召回数量 `K` 和最终返回数量 `Top-K`；

固定 `Top-K=5` 时，开发集的关键结果如下：

| K | 严格证据命中率 | 结论 |
| ---: | ---: | --- |
| 20 | 23/33（69.7%） | 候选不足，部分正确证据未进入重排阶段 |
| 30 | 26/33（78.8%） | 命中率提升明显 |
| 32 | 26/33（78.8%） | 没有额外提升 |
| 35 | 26/33（78.8%） | 没有额外提升 |

**K 从 20 增加到 30 时，开发集严格证据命中率从 69.7% 提升到 78.8%；继续增加到 32、35 没有额外提升，所以选择达到最佳效果的最小 K，即 30。随后在 17 道验证题上得到 15/17、88.2% 的严格证据 Hit@5。**

随后固定 `K=30` 比较 `Top-K`：

- `Top-K=3`：25/33（75.8%）；
- `Top-K=5`：26/33（78.8%）；
- `Top-K=7`：26/33（78.8%）。

因此当前线上配置为：FAISS 粗召回 **K=30**，Cross-Encoder Reranker 重排后向 LLM 提供 **Top-K=5** 条证据。选择它不是凭感觉，而是在**固定语料、Embedding、切分方式和 Reranker**后，用开发集比较质量与开销得到的结果。

## 7 月 28 日补充：AnySearch 接入学习

> 本次主题：学习将第三方搜索 API 接入法律 Agent，并将不同服务的返回结果转换为统一格式。

这与原本 DuckDuckGo/ddgs 在项目中的结果格式一致。后续 Agent 只需要处理统一字段，而不需要知道搜索服务具体来自 AnySearch 还是 ddgs。

### 三个函数的职责划分

- `_request_anysearch_payload(query)`：只负责发出 HTTP 请求，并返回原始 `payload`；
- `_format_anysearch_results(payload)`：只负责 JSON 解析、类型检查和格式转换；
- `_search_with_anysearch(query)`：组合前两步；没有有效结果时抛出异常，由外层决定是否启用 ddgs 兜底。

这种拆分体现了单一职责：网络请求、数据解析和业务兜底不混在同一个函数里，出现问题时更容易定位，也方便以后替换搜索供应商。

###  今天学到的概念

| 概念 | 在本项目中的含义 |
| --- | --- |
| JSON 解析 | 将 `response.json()` 返回的 Python 数据取出为 `data → results` |
| `payload: object` | 外部 API 返回的内容不一定是字典，因此先按通用对象接收，再用 `isinstance` 检查 |
| `raw_results` | 尚未整理过的原始搜索结果列表 |
| `item` | 循环中取出的单条搜索结果字典 |
| `item.get("title", "")` | 安全取字段；字段不存在时返回默认值，不让程序因为 `KeyError` 中断 |
| 数据标准化 / 适配层 | 将不同供应商的字段转成项目统一的 `title/body/href` 格式 |


### 面试 / 复述版

> 我把第三方搜索接入拆成请求、解析和统一输出三层：请求层负责鉴权、超时和 HTTP 错误；解析层将供应商 JSON 转成项目统一的 `title/body/href`；组合层负责将异常交给外层，以便后续回退到 ddgs。这样替换或新增搜索供应商时，不需要修改 Agent 主流程。

### 完成联网搜索的主备切换

在完成 20 题服务对比后，正式将联网搜索工具改为：

```text
web_legal_search
  → 优先调用 AnySearch
  → 超时、HTTP 错误、解析失败或空结果时回退到 ddgs
  → 两者都失败时返回友好提示，不暴露底层异常信息
```

*实现时保留一个 Agent Tool：LLM 只负责判断“是否需要联网搜索”，不需要在 AnySearch 和 ddgs 之间做额外选择；具体供应商切换由工具内部完成。*

- `_request_anysearch_payload`：读取环境变量中的 Key，发起带超时的 HTTP 请求；
- `_format_anysearch_results`：将 AnySearch JSON 转为统一的 `title/body/href`；
- `_search_with_anysearch`：组合请求与解析；无有效结果时抛出异常；
- `_search_with_ddgs`：提供同样输出格式的备用搜索；
- `web_legal_search`：处理主服务、备用服务与最终文本格式化。

完成了三层验证：

1. **主路径直接验证**：使用真实 `.env` Key 调用 `web_legal_search`，日志显示 `provider=anysearch status=ok duration_ms=2939`；返回了国家市场监督管理总局 `samr.gov.cn` 的《中华人民共和国消费者权益保护法》结果。
2. **兜底直接验证**：在单次 Python 进程中设置无效 Key，得到 `provider=anysearch status=fallback reason=HTTPStatusError`，随后 `provider=ddgs status=ok duration_ms=3702`，并正常返回搜索文本。该测试不修改 `.env`。
3. **网页端到端验证**：重启 FastAPI 后，浏览器调用 `/legal/chat/stream` 返回 `200 OK`；日志显示 `provider=anysearch status=ok duration_ms=4092`，说明真实 Agent 链路已经使用新主路径。

端到端网页请求总耗时为约 `199539ms`。其中已有日志的向量库加载、向量检索、AnySearch 和 Reranker 合计约 `21.8s`；剩余约 `178s` 尚未按阶段拆分。

因此不能把长等待简单归因于联网搜索：AnySearch 在这次请求中约 `4.1s`，Reranker 约 `13.7s`。下一步应在 Agent 内部补充 Planner、LLM 工具决策和最终回答生成的分阶段耗时日志，再依据数据确定下一轮优化点。

### 2. 刷新页面后如何恢复会话

问题不是 SQLite 没有保存数据，而是此前前端每次刷新都会生成新的 `session_id`，并且没有主动调用后端的会话读取接口。因此数据库里有记录，但浏览器不知道该恢复哪一场会话。

现在的流程是：

```text
浏览器首次进入
  → 生成随机 session_id
  → localStorage 保存当前 session_id
  → 用户发送法律咨询，后端按该 ID 写入 SQLite

刷新页面
  → 从 localStorage 取出 session_id
  → GET /legal/session/{id}
  → 读取 history + case_summary
  → 恢复当前对话与侧栏案情摘要
```

实现位置：`frontend/src/App.tsx`。

- 使用浏览器的 `localStorage` 保存**当前**会话 ID；
- 使用 `crypto.randomUUID()` 生成更难碰撞的会话 ID；
- 恢复请求返回后，将数据库中的 `history` 重新转换为前端的 user/bot 消息；
- 使用 `restoreVersionRef` 防止“刷新后的恢复请求较慢、用户已发送新消息”时，旧恢复结果覆盖新界面。

这不是登录系统：它只能恢复当前浏览器的当前会话，侧栏完整历史列表不跨刷新保存；而且快速问候语由前端直接回复，不会写入 SQLite。这些是当前本地 Demo 有意保留的边界。

### 6. 面试高频题与回答思路

#### Q1：为什么用 SQLite，而不是 PostgreSQL？

> 当前项目是单机、低并发的作品集 Demo，SQLite 不需要单独部署数据库服务，却能解决“Python 内存重启即丢失”的问题，所以开发成本最低。我用 `sessions` 保存会话摘要，用 `messages` 保存逐轮消息，通过 `session_id` 关联。若以后需要多实例部署、多个服务共享会话、更高并发或用户权限控制，再迁移 PostgreSQL，而不是一开始过度设计。

#### Q2：SQLite 已经保存会话，为什么刷新页面仍可能看起来没有记忆？你怎么修？

> 后端保存和前端展示是两件事。之前刷新会生成新 `session_id`，前端也没有请求已保存的会话，所以 UI 看起来像失忆。我的修复是让浏览器把当前 ID 保存到 localStorage，刷新时调用 `/legal/session/{id}`，把 `history` 和 `case_summary` 转回前端状态。这样明确区分了“数据库有没有数据”和“前端有没有加载数据”。

#### Q3：为什么要用 UUID，而不是 `Date.now()` 作为 session_id？

> `Date.now()` 主要依赖毫秒时间，碰撞概率较低但可预测；UUID 的随机性更好，更适合作为本地会话标识。我不会把它当成权限认证：当前项目没有登录和会话归属校验，所以仍然只用于本地 Demo。

#### Q4：恢复历史时可能出现什么并发问题？

> 刷新后会发一个异步读取请求。如果用户在请求返回前已经发送新消息，迟到的旧历史可能覆盖当前消息。我在前端给恢复请求加版本号：新建会话、切换会话或发送消息都会更新版本；只有版本仍一致的恢复结果才允许写入页面。这是一个轻量的异步竞态保护。

#### Q5：为什么测试 SQLite 时不直接测完整 Agent？

> 完整 Agent 会依赖远程 LLM、本地 Ollama、FAISS、Reranker 和联网搜索，慢且结果会受网络、模型与费用影响。SQLite 回归测试的目标是验证存储合同，因此把数据库指向临时目录，只测保存、读取、隔离和顺序。分层测试可以更快定位问题：存储错了先看存储，模型效果问题再用评测集验证。

#### Q6：`py_compile`、前端构建和回归测试分别解决什么问题？

> `py_compile` 只检查 Python 语法；前端构建检查 TypeScript 类型和打包是否成功；SQLite 回归测试验证具体行为是否符合预期。三者互补：能编译不代表逻辑正确，测试通过也不代表线上模型回答一定正确。

#### Q7：为什么补 `.env.example` 和 `.gitignore`？

> `.env.example` 让别人知道需要哪些环境变量，但不暴露真实 Key；`.gitignore` 防止数据库、简历、Word 临时文件和本地配置误提交。这是最基础的可复现性和敏感信息管理，不是为了“好看”。

#### Q8：既然项目还能优化，为什么选择现在停止？

> 我用“是否显著提高真实演示和可验证能力”作为优先级标准。核心工作流、检索评测、联网主备、会话持久化和最小回归测试已经形成闭环。Docker、PostgreSQL、多 Agent、MCP、完整监控平台都可以做，但对当前求职的边际收益较低。我把它们记录为后续方向，把时间投入投递、面试和第二个业务流程项目。

#### Q9：为什么当前不建议直接公网部署？

> 当前没有用户认证和会话归属校验，`/legal/session/{id}` 会返回会话内容；法律咨询也可能包含敏感信息。虽然已经默认限制为本机监听和本地 CORS，但公开部署前还需要认证、授权、敏感数据策略和审计，不能把“本地能跑”误说成“生产可用”。

### 上下文管理
我实现了**三层上下文截断策略**。
第一层是**数据库层**，SQL 查询用 ORDER BY id DESC LIMIT 100，避免了**全量加载**。第二层是 **Agent 层的滑动窗口**，**保留最近 12 轮原文传给 LLM，超出部分丢弃**——但**关键案情已经由 case_summary 压缩吸收了**。第三层是 **Planner 的上下文增强**，之前 Planner 只看最新一条用户消息，导致追问时上下文断裂；我改了之后它能**看到最近 3 轮完整对话**，能理解用户的简短回复在回答什么。

设计原则是关注点分离：数据库管存取不替业务做决策，*Agent 层决定给 LLM 看多少*，case_summary 做*兜底压缩*。后续计划加入 LLM 摘要压缩层，把超出窗口的旧消息自动压缩为结构化摘要。"

### 为什么 SQL 要加 LIMIT？什么是全量加载？

SQL 不加 LIMIT 时，`SELECT * FROM messages WHERE session_id = ?` 会把**这个会话的全部消息**取出来。对话越长，返回的行数越多——100 轮就是 200 行，500 轮就是 1000 行。SQLite 不会自己判断"够了吧，给 100 条就行"，它严格执行命令：你要全部，就给你全部。

`LIMIT 100` 是一个**防御性设计**——跟写 try/except 同一个道理：不是每次都会出异常，但你需要兜底。当前法律咨询场景很少超过 30 轮，但万一未来接入其他场景，数据库层不会因为一次查询加载几千条记录。

### 什么是解耦（Decoupling）

**解耦 = 把两个东西拆开，各自独立，改一个不影响另一个。**

耦合的坏处：
```
legal_agent.py 里面直接写幻觉检测代码
→ 改幻觉逻辑要动 agent 核心文件
→ 测试幻觉也得启动整个 agent
→ 两个东西绑死在一起，一个出问题拖累另一个
```

解耦的好处：
```
agent/hallucination_guard.py  ← 独立文件
  └─ check_hallucination(answer, docs)

legal_agent.py
  └─ from agent.hallucination_guard import check_hallucination
  └─ 只调一行函数
```

项目中已有的解耦例子：`rag/retriever.py` 和 `agent/legal_agent.py` 是分开的——检索逻辑改了，Agent 核心代码不用动。这就是"高内聚、低耦合"。

### 幻觉检测

#### 法律 Agent 的五种幻觉类型

| 类型 | 例子 | 严重程度 |
|------|------|----------|
| 法条编号捏造 | LLM 说"消保法第 55 条"，但该法根本没第 55 条 | 🔴 |
| 法条内容虚构 | 编了一段听起来像法条但不是的内容 | 🔴 |
| 张冠李戴 | 说的是消保法，却标成了"产品质量法第 X 条" | 🟡 |
| 无视检索结果 | RAG 搜到了正确法条，LLM 没采用，凭记忆瞎编 | 🟡 |
| 过期法条 | 引用的法条已被修订，LLM 不知道 | 🟡 |

#### 检测方案：两层防御

**第一层：引用校验（Citation Verification）— 零延迟**
- 用正则提取 LLM 回答中的所有"第X条"引用
- 逐个去检索返回的文档里查是否存在
- 不存在 → 标记 🚨
- 抓的是：法条编号捏造

**第二层：检索覆盖度检查（Retrieval Coverage Check）— 零延迟**
- 提取回答中的关键实体（法条名、金额等）
- 和检索结果做文本重叠度对比
- 大部分实体在检索结果中找不到 → 标记 🚨
- 抓的是：无视检索结果、凭记忆瞎编

两层都不增加 LLM 调用，零额外延迟。检测结果作为警告标记追加到回答末尾，而不是截断回答——把判断权留给用户。

## 7 月 31 日补充：工具选择评测——从 8% 到 76% 的诊断与优化

> 本次目标：让维度 2「工具选择准确率」能真正跑起来，定位所有阻碍因素，逐步优化到可交付的水平。

### 1. 背景：为什么 8% 是假的

上一轮评测显示工具选择准确率只有 8%，但仔细看日志发现 `actual_tools=[]` 遍布所有题目。根因是 **Planner 在 LLM 之前截断了所有评测请求**——评测题本身不会提供完整的事件时间/损失/诉求，Planner 判定信息不完整 → 追问用户 → 流程结束，LLM 根本没机会看到题目，更不可能调用工具。

这不是 LLM 不会选工具，而是**评测环境与 Agent 架构的配合问题**：Planner 是为真实用户对话设计的，评测是自动化批量调用，两者逻辑冲突。

### 2. 解法：`skip_planner` 标志

在 `AgentState` 中新增一个 `skip_planner: bool` 字段：

```text
正常用户对话：
  START → Planner（检查信息完整性）→ LLM ⇄ Tools → END

评测模式（skip_planner=True）：
  START → Planner（跳过，直接放行）→ LLM ⇄ Tools → END
```

实现要点：
- `call_planner()` 开头检查 `state.get("skip_planner", False)`，为 True 时直接返回 `{"info_complete": True}`，不再调 LLM 做信息检查
- `run_legal_agent()` 新增 `skip_planner` 参数，透传给 `_compiled_graph.ainvoke()`
- `main.py` 的 `ChatRequest` 新增 `skip_planner: bool = False` 字段，透传给 `/legal/chat` 端点
- 评测脚本 `evaluate.py` 发请求时携带 `"skip_planner": True`

这是一个典型的**特性开关（feature flag）**：不改动主流程的业务逻辑，只在特定场景下切换行为。生产对话不受影响，评测获得直达 LLM 的路径。


**第一次重写**（把最高优先级规则提到开头、缩短）：
```text
⚠️ 最高优先级规则：回答法律问题前，你必须先调用工具检索法条。
即使你确定知道答案，也必须先用工具确认。严禁不经检索直接回答。
```

**追加保险——动态检索提醒**：在用户消息末尾直接注入指令：
```python
_retrieval_reminder = "\n\n[系统指令：请先调用 legal_rag_search 检索法条原文，再根据检索结果回答。不要凭记忆直接回答。]"
messages.append(HumanMessage(content=user_input + _retrieval_reminder))
```

为什么这样做？System Prompt 在消息列表最前面，距离 LLM 决策点很远（中间隔着对话历史、案情摘要、用户消息）。把指令直接拼到用户消息末尾，离 LLM 即将生成的 tool_calls 最近，更不容易被忽略。这是利用 LLM 对**最近上下文更敏感**的特性。

#### Q1：你的工具选择准确率怎么测的？

#### Q2：为什么需要 skip_planner？

### 9. 技术话术（需要理解的概念）

| 概念 | 在本项目中的含义 |
|------|------|
| Feature flag / 特性开关 | 通过 `skip_planner` 布尔值切换行为，不改主流程代码 |
| 429 Rate Limiting | API 服务商按账户限制请求频率，超限返回 HTTP 429 |
| Rate Limit 自愈 | 检测到 429 后自动延长等待时间，而不是直接失败 |
| 动态提醒 / Prompt Injection | 把指令拼到用户消息末尾，利用 LLM 对最近上下文的偏好 |
| Instruction following | 模型遵循 System Prompt 指令的程度；GLM-4.7 在这方面偏弱 |
| Tools 调用 vs 凭记忆回答 | Agent 场景的核心分歧：工具检索（准确但慢）vs 模型记忆（快但可能幻觉） |

**为什么不用 LLM 自检作为主要手段？**
LLM 自检（让模型再看一遍自己的回答有没有问题）更准，但每轮多一次 API 调用，增加 2-5 秒延迟。规则检测更快、更可解释、更容易写测试。正确的策略是：先跑规则，规则兜不住的场景再考虑 LLM 自检。

  ### 补充 1：量化为什么"快还不掉准确率"

  **量化是什么**：模型里每个权重本来是一个 float32 数字（占 4 字节，能表示很大范围的精确小数）。量化把它换成 int8 整数（只占 1 字节）。相当于把照片从"高清原图"压成"压缩格式"——文件小、打开快，肉眼看不出差别。

  **为什么快**：权重体积缩到约 1/4，内存读写变少；CPU 做整数运算也比浮点快。

  **为什么准确率不掉**：*Reranker 的工作是给每对（问题，文档）打分，然后按分数排序取前 5。它只关心"谁比谁高"，不关心分数精确到小数点后几位*。压精度后每个分数有一点点偏差，但相对顺序基本不变，Top-5 就几乎不变。

  **验证数据**（同一套 17 道验证题，唯一改动 = 量化）：

  | 指标 | 量化前 | 量化后 |
  | --- | ---: | ---: |
  | 严格证据命中率 | 15/17（88.2%） | 15/17（88.2%） |
  | Rerank 平均耗时 | 9542ms | 5738ms |

  ### 上下文管理的话术
  大模型上下文窗口有限，所以对话管理我分四层：

④ 压缩：被截断的旧对话，关键信息由**案情摘要**吸收——结构化 5 个字段、每轮后台异步更新，再注入模型。

###  实际应用中 PDF 长啥样？图片怎么办？

真实世界的法律 PDF 大概分三类：

类型	长啥样	怎么处理
**文本版**	政府/人大官网发布的，有文字层	直接提取。但排版多样：单栏、两栏、页眉页脚、表格、跨栏条款编号
**扫描版**	就是图片，没文字层	必须 OCR（中文用 PaddleOCR，整页是图时）
**混合版**	文字 + 盖章页图片 + 表格 + 水印	检测无文本的页 → 单独 OCR
图片的坑比你想的多：

整页是扫描图（无文字层）→ 整页 OCR
只有某几页是图（如红头文件盖章页）→ 只 OCR 那几页，别浪费
图片里有表格、印章 → OCR 还要做版面分析才知道哪块是标题、哪块是条文
工业级做法是**版面分析（layout parsing）**：先识别页面结构（标题/段落/列/表格/图片在哪），再按正确顺序拼回文本。中文场景常用 MinerU（PDF-Extract-Kit） 或 PaddleOCR 的 PP-Structure——它们能自动处理分栏，就是重一点。
