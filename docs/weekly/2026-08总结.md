# 传统 RAG  VS agentic RAG

传统RAG是一条管道(固定流水线),原料进去,产品出来,中间没有分支,每步顺序固定，没有回头路。query → 无条件检索一次 → 拼进 prompt → LLM 生成 → 结束

agentic RAG RAG在这里变成一个检索的工具,由大模型来决定什么时候查,查什么,查几次

# React

React=reasoning（思考）+acting（行动）

Thought（想：我需要查什么）→ Action（调工具）→ Observation（看结果）→ 再 Thought…

首先先思考我需要什么，然后调用工具拿到结果，在进行思考，直到能回答为止，同时我还设置了**防死循环的兜底限制**，最多调用五轮工具

适合比较灵活复杂的任务可以边想边做根据具体情况进行调整

## chain of thought,plan and execute

chain of thought主要是让模型通过中间步骤一步步得到答案,它强调的是reasoning,也就是模型内部的分步思考,它比较适合逻辑数学这种**不一定需要调用外部工具**的任务.

# MCP 模型上下文协议


解决的是**AI应用怎么接入外部工具/数据源的标准化问题**//*工具跨模型复用的标准化问题*，是工具接入AI应用的标准化协议。 MCP里面通常有host client server三个角色，host是AI应用，client负责连接host和server ，server负责暴露外部工具，资源，和提示词，是外部能力提供方。

通过MCP 工具按照统一协议实现一次就可以被不同的agent平台调用


## 步骤

1. MCP server启动时**声明我有什么工具,调用工具** /把工具从按照MCP协议包装成server,client连接server调用tools list拿到工具列表.

2. MCP **Client 连接把MCP工具转换成不同模型需要的function calling格式**

3.**模型调用**，模型本身完全不知道MCP的存在，因为client已经转换成了各自模型所需要的格式

4. 模型决定调用client拿到name,args。调用tool_calls发送给MCP server， server真正执行工具逻辑返回content，client拿到结果,包装成Toolmessage，送回模型

###  流程

tool_calls 是模型发出的请求，tool_message 是工具执行后的回包，靠 tool_call_id 做全链路追踪和并发配对。没有这一步，ReAct 循环就断了，模型看不到工具结果，整个 Agent 就废了。

# workflow


工作流是llm和工具**在预先定义的代码路径**编排的系统，控制权在代码手里，反过来**他的对立面**是agent， agent是大模型动态自主指挥自己的流程和工具使用的系统。*可以让workflow管理主流程，而agent去处理具体的复杂的节点*

Workflow的控制流在代码里面，确定性，可测试，可审计。agent的控制流在LLM里面，概率性,可推理，自适应

## 背景理解

早期大家把所有的逻辑都交给提示词，让大模型自己去想办法，*但是结果是同样的输入，每次输出不一样*。然后关键的决策，就比如说合规检查，权限校验，是不能交给概率模型的。然后**确定性的部分**我们必须要把它写成代码里面的**状态机/图**，这就变成了workflow。剩下的灵活性必须推理的部分交给这就是agent


## workflow和agent结合

1. Workflow作为主流程，把agent放到某些智能节点中，比如说让agent去做文档总结，异常分析，或者是代码审查

2. agent作为决策者，判断某个任务适合某个标准流程后，调用workflow

3. 让agent去处理workflow中不稳定的，非结构化的节点，比如说意图识别，异常处理，和方案生成

# agent loop/agent 循环


*是llm完成任务的一个核心循环*,一般包括读取任务,思考判断,执行工具,返回结果,观察反馈,更新状态,判断是否继续.

每一轮agent会根据上下文和当前目标决定下一步,工具执行后返回observation,然后更新state,再进行下一轮决策,它存在的作用是让agent可以处理复杂,多步骤,不确定的任务.为了避免死循环一般会设置轮数


# agent runtime

**负责让agent真正跑起来的运行框架**,负责管理agent的状态,调用LLM,执行循环,工具调用,记忆,异常处理,权限控制和日志追踪.

大模型本身只是推理模型,而agent需要不断地进行规划行动观察和反馈,runtime就**负责调度这些板块**,让agent可以稳定地完成多步骤任务.



# agent harness 

是包裹在agent外层的**控制和测评框架**,用来*给agent提供标准化任务环境*,限制权限记录,执行过程,并验证最终结果.非业务逻辑几乎所有agent一样，所以被抽出来当成Harness

## 功能

包括工具管理，会话持久化，上下文压缩,子agent编排，权限控制，日志追踪，沙箱


## 说一下对于deepseek harness 的理解

它的一个设计思想就是**少做预设，让模型发挥它的原生能力，还有一个就是万物皆插件**。llm路由， agent循环，工具运行时，会话持久化，沙箱，前端UI都做成可以插拔的模块。每个功能是一个npm包，新加功能时不用改源码。它的插件主要分六大类,分别是LLM网关插件层，agent编排插件层，工具运行时插件层，会话持久，安全与沙箱插件层，宿主与前端插件层。



# agent

**大模型为决策中心的智能体**,通过工具调用与环境交互,具备调用工具,记忆,规划和反思的能力,通过多步迭代完成任务


# 介 绍 项 目

这个项目是基于 LangGraph、RAG 和 FastAPI 的法律智能问答系统。整体流程是：用户提问先到前端，除少量固定问候语走快速回复外，其余消息都会经过 Planner 节点——它固定调用一次大模型做五分类意图识别，区分客观知识查询、个人案情咨询、闲聊、无关内容和情绪宣泄。只有个人案情咨询才会检查四个关键维度：事件、时间、损失、诉求，信息不全就追问，齐了才放行进入 ReAct 循环。循环里大模型自主决定调用两个工具：本地法条库的混合检索，FAISS 向量加 BM25 词面双路召回、RRF 融合后用 Reranker 精排 Top-5；另一个是联网搜索，主搜索失败自动兜底。工具结果返回后模型整合答案，先过幻觉守卫的两层规则校验，再通过 SSE 流式输出给前端，同时在后台更新案情摘要、持久化到 SQLite，刷新后会话仍可恢复。

# 讲 一 下 检 索 的 阶 段

我的检索过程一共分四个阶段：FAISS 向量召回、BM25 召回、RRF 融合、Reranker 重排序。

启动时先做 BM25 的分词和建索引（一次性的），同时 FAISS 的向量库也是启动时建好。

FAISS 向量召回选 K=40，BM25 词面召回选 K=20，两路通过 RRF 融合成 40 篇候选，
再经 BGE Reranker 重排序输出 Top-5。

最开始我用的是纯向量检索，发现它在短锚句召回上比较弱——
比如"销售者赔偿后……"这种 10~17 字的法条引用，向量化后语义稀薄。
后来加了 BM25，正好补这个缺口，因为 BM25 的强项就是词面匹配。

两路召回分数度量不同（FAISS 是 cosine，BM25 是 BM25 score），
不能直接比，所以用 RRF——只看排名不看分数，
公式是 1/(k+rank) 相加，k 取 60。

Reranker 太慢了，我做了动态量化——
float32 权重压成 int8，体积缩到 1/4，
实测 Rerank 耗时从 9542ms 降到 5738ms（-40%），
但严格证据命中保持 88.2% 不掉。

最后选出 Top-5 喂给 LLM。

补充 BM25 公式三个核心因子：
  1. TF 词频饱和：出现越多越相关，收益递减
  2. IDF 逆文档频率：稀有词更值钱，区分度高
  3. 长度归一化：同样命中，短文档赢

BGE Reranker 用 Cross-Encoder，
把 query 和 doc 拼接一起输入模型直接打分，
比 Bi-Encoder（向量检索）准但慢——
Bi-Encoder 是分别编码成向量再算相似度，会丢失交互信息。


# 工 具 的 schema 信 息 是 在 哪 一 步 注 入 的

**工具如果想要能够被LLM调用,就必须要知道这个工具有什么参数,参数是什么类型,这就是Json schema**

*函数签名function signature*：函数的名字和参数列表，包括参数名默认值是否必须要填类型

bind_tools:*把函数签名和docstring起变成JSON格式,在大模型调用的时候,一起注入到deepseek API里面*（{"name": "legal_rag_search", "parameters": {"query": {"type": "string"}}}）

工具呢schema不是手写的,而是bind_tools的时候用函数签名和docstring自动生成的,每次调用模型时schema会随着请求注入模型,根据这个来决定如何去调用如何去谈参数

# function calling

首先llm需要知道工具的参数，也就是Json schema,然后大模型会对需要什么工具根据Json schema进行一个判断,输出tool_calls里面包含了他要调用什么工具,然后解析tool calls,进行工具的调用.将调用完的结果返回给大模型生成答案,这就是整个function calling的过程


# 多 agent 的 任 务 拆 分 不 清 楚 怎 么 办

首先任务拆分是让大模型自己去做的，但是模型具有随机性，**同一个任务拆除的子任务可能不一样，然后任务的边界模糊混乱**，就比如说b要a的输出，但如果a执行失败了怎么办？信息就会在agent的传递间丢失，递归拆分可能会失控。所以**生产上经常用workflow定死拆分逻辑**，只在复杂节点内部用agent



# function calling VS MCP

Function calling是**模型调用工具**的协议而MCP是**工具跨模型可以复用**的协议，他们不在一个层面上。
然后MCP解决了function calling的痛点，每个大模型的工具描述格式不一样，每个工具接入都需要重写一遍适配代码，

# 上 下 文 压 缩

分层记忆：把**记忆按"价值"分几层**放——① 窗口内：*最近几轮原文直接给模型*；② 摘要层：窗口外的历史压缩成*摘要*（你的 case_summary）；③ 向量层：**历史片段存 embedding，按相似度检索召回**。你项目已经做了前两层（历史截断 12 轮 + case_summary）。

向量记忆：把"用户说过的事实片段"（比如"我父亲 2020 年工伤""我之前咨询过劳动仲裁"）用 embedding **存进向量库，每次对话前检索相关的旧记忆注入**——解决"跨会话长期记忆"和"海量历史装不进窗口"的问题。代表：mem0、LangGraph Store、Zep。

# agent 一直循环 调用工具 怎么办

1. **设置Langgraph递归上限**我设置的是大概五轮的调用，是*全图节点调用次数上限*，包括LLM节点tools节点在内的所有节点执行次数

2. **工具调用去重**，模型反复地去调用一个工具掉N次

3. **最大工具轮次**。限制工具的调用轮次，不限制LLM推理的轮次

4. **循环模式检测**，A-B-A-B-A....这样的反复调用，去维护一个滑动窗口

5.写清楚**系统提示词**，每个工具最多调用一次，如果工具返回·未找到·，不要重复去调用

首先要写清楚*系统提示词*我告诉他每个工具最多顶只能调用一次当返回没有结果的时候不要再重试了..。然后为了防止大模型反复调用一个工具多次，我选择建立一个*名字和参数的缓存*，当第二次调用这个工具的时候，会直接把上一次的结果返回给它，同时在*tool message里面告诉他不要再重复调用工具*了。然后再就是*设置最大工具轮次*，我所设置的是五轮，再就是为了防止AB AB工具循环调用，设置了一个*滑动窗口*，将它切成两半，如果前后一样的话，那么直接进行一个熔断。

# RAG的完整流程

RAG = Retrieval-Augmented Generation = 检索增强生成

让 LLM 在回答前先查知识库，把检索结果作为上下文喂给模型，减少幻觉。

User提问--->问题理解---->进行检索---->提示词构造---->大模型生成回答------>后处理

用户问题
   ↓
①*Query 理解*（可选：改写、扩展、提取实体）
   ↓
② *检索*（向量 + BM25 → RRF → Reranker → Top-K）
   ↓
③ *Prompt 构造*（system + 检索结果 + 用户问题）
   ↓
④ *LLM 生成回答*
   ↓
⑤ *后处理*（幻觉检测、流式输出、持久化）

## prompt 构造

┌──────────────────────────────────────┐
│ Layer 1：System Prompt（固定）       │  ← Agent 身份 + 行为守则
├──────────────────────────────────────┤
│ Layer 2：检索结果（动态注入）        │  ← "检索到的法条：..."
├──────────────────────────────────────┤
│ Layer 3：用户问题（动态）            │  ← 用户原始输入
├──────────────────────────────────────┤
│ Layer 4：案情摘要（动态，可选）      │  ← case_summary 上下文
└──────────────────────────────────────┘

tips:检索结果放在prompt之后,用户问题之前,先看规则再看结果最后回答.

这是因为大模型对最近的内容更敏感,对开头的内容注意力会衰减
┌─────────────────────────────────────────────┐
│ Position     │ Attention 权重 │ 影响力       │
├──────────────┼────────────────┼──────────────┤
│ 开头（System）│ 中等          │ 定义身份和规则 │
│ 中间（检索）  │ 低            │ 容易被忽略     │
│ 结尾（User）  │ 最高          │ **影响最大**   │
└─────────────────────────────────────────────┘

## RAG VS 微调

微调就是根据知识库去对应模型进行训练，然后它的知识更新速度很慢，需要花费的成本也很高，而且它本质是个黑盒，如果出错了不好去调查。

RAG他的知识库是可以实时更新的，成本也是比较低的，就是检索和推理。然后也可以解释性比较高，因为可以看到引用的法条。

## RAG检索结果检索不到怎么办？

1. 检索不到可以使用*联网搜索*
2. 可以使用*对问题进行重写*HYDE重新进行检索
3. 最后可以*使用自己的知识进行回答*，但要提示用户注意核实
