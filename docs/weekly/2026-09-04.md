## 开始学Redis

**一个开源的，把数据存在内存中，以KEY-VALUE结构组织的软件，单线程执行命令**



主板（一块大电路板）
 ├── CPU   ← 一小块芯片，负责"计算"，速度极快
 ├── 内存条 ← 长条形的小板子，插在主板插槽上（就是你买电脑说的"16G内存"）*内存 RAM* **小，快，断电就没**
 └── 硬盘  ← 一个方块/小卡片（机械硬盘是大方块，固态硬盘是小卡片），存文件用的*硬盘，C/D盘* **慢，永久保存**

###  内存条和硬盘的保存方式

内存条是靠*电荷记录数据*的物理器件，电一停电荷就漏光。**硬盘（尤其机械/固态）记录方式不依赖电，所以永久保存**。这就是"文件没保存就关机就丢了"的根源——你打开文件时它被从 硬盘搬到内存 里编辑，保存 = 再从 内存写回硬盘


### 缓存是啥

为加速访问，将昂贵计算/查询的结果在快速介质中保存一份副本的机制，

命中：用之前已经有的答案，**请求的数据在缓存中有答案**

未命中：之前也没有这个答案，然后重新走一遍，再把答案存进缓存里面


### Redis快的原因

1.  **Redis 的数据都放在内存里面**。只放"丢了也没关系、大不了重新算"的数据（缓存）

2. **Redis采用单线程**。拿数据很快，所以*瓶颈不在拿数据而是协调数据*，干脆采用单线程

3. **网络IO多路复用**

epoll解决了*没消息还在查的浪费*，让一个线程监视大量连接，有事件的连接才通知

`磁盘IO`,从磁盘读文件，慢在机械寻道/搬运数据，比内存访问慢百倍级。  

`网络IO`，从网络收发消息，慢的根源是等待远端响应（可能几十毫秒~几秒），期间程序无事可做。


线程： CPU调度的最小执行单位，一个程序可以同时开多个线程并行干，同时共享一份内存

### 3个机制

1. TTL time to live  **存活时间**   为每个key设置的过期时间,到期后redis自动删除该key

因为缓存的数据可能会过时


2. **内存淘汰**

当内存达到上限的时候,按照既定策略删除一部分旧数据腾地方的行为。

策略主要有两种：allkeys-lru第一种就是哪条KEY最久没被访问就先删哪条。

volatile-lru第二条是*只在设了ttl的KEY*里面按照LRU删

LRU  最近最少使用

3. **持久化**

把内存里面的数据写入磁盘，使redis重启/断电后能恢复的机制

### 缓存三种失效的情况

缓存不是用来加速的，*是用来保护后面那个又贵又慢的东西（数据库/LLM API）*

以下是三种"保护失效、压力漏到后面"的事故

1. **穿透**

大量请求查询根本不存在的数据，缓存永远 miss，请求全部落到数据源。


**空值缓存**：查过没有？把 key → 空 也缓存，TTL 设很短（如 60 秒），下次穿透直接命中"空"

**布隆过滤器**：一个超省内存的概率型数据结构，能秒答"这个 key 一定不存在"（直接拦截）或"可能存在"（放行）。一句话定义：花 1MB 内存挡住 99% 的假查询。

2. **击穿**

*某个高频热点 key* 恰好过期的瞬间，海量并发同时 miss未命中，同时回源，数据源被瞬时压垮。

核心就一个思想：只让一个人去回源，其他人等着抄答案

互斥锁：第一个请求拿到锁去回源，其余请求等待；回源的人写完缓存，后面的人全部命中

3. **雪崩**

*大批 key 在同一时刻集体过期*（或 Redis 整个宕机），回源流量像雪崩一样压垮数据源。

a. TTL 加随机抖动：3600 + random(0,600)，把集体过期摊成缓慢 trickle
b. 多级缓存：进程内字典先挡一层，Redis 再挡一层
c. Redis 高可用（哨兵/集群）——了解名词即可


### 实操

环境：redis 库进 .venv；学习容器 redis-learn 端口 **6380**（6379 被 context-engine-redis-dev 占着，勿连——实验用 flushdb）。

**第 1 课 set/get**：`r = redis.Redis(...)` 是一条网络连接，字典活在 Redis 里。**set 是盖不是加**；查无此 key → None = miss。

**第 2 课 TTL/INCR**：`ex=20` 装倒计时，到点自动删；ttl=-1 永生=慢性病。INCR 原子（掏→加→塞一口气办完），get+set 两条命令有空档会被插队。军规：**能一步做完的事绝不留给两步**。限流器 = INCR + EXPIRE（忘 expire → "每分钟10句"变"一辈子10句"）。

**第 3 课 并发覆盖事故**：两线程 500 轮"读→写"，期望 50000 实际蒸发数千。根因=**两条命令之间的空档**（不是发呆，删 sleep 也只是变少不消失）。修复：incr 替换读+写 → 精确 50000。坑：key 写成变量名 `bal`，往错柜子加钱——key 必须一字不差。

**第 4 课 锁**：incr 治不了"先判断再行动"（看余额→扣钱是两条命令）→ `with lock:` 把组合动作圈成不可打断的整块。纪律：门里事少、必还钥匙（with 保证）、别互相等（死锁）。
下一步：`SET k v NX EX 10` 跨机器抢锁（nx=互斥，ex=防死锁）→ 击穿互斥锁 → lab4/5。

### 锁

为什么会需要锁，原因就是数据共享和并发。两个线程共享一份数据，它们会各自执行读该写。其中读和写是两条命令，中间有空档可以进行插队，所以就有了第一层解法是*原子命令*。

把读改写合并成一个命令，单线程排队，一口气办完。解决的问题是*不需要思考只需要操作*的问题但是如果要先进行判断在进行操作的话，中间还是会有缝隙。

虽然组合动作之间还是有缝隙，最后把整段圈起来同一时刻只允许一个人进这就是锁

然而*当不在一个进程内*变成了两台机器上的两个后端进程，就必须要采用分布式锁。因为🔒是进程私有内存里面的对象.

SET NX EN

got = r.set("lock:demo", name, nx=True, ex=10)


ex=10   宕机的进程没有办法还锁，所以当程序十秒后都没有反应就直接删除


因为 SETNX 是 “SET if No eXists”，它是服务器端的一步指令：

“检查 + 写入”，要么全做成，要么全不做，中间不允许插队。这就像自动门，一个人进去的一瞬间，门就锁上了，谁也插不进去。

#### 🔒总结

并发下"读—改—写"会被插队，*单步操作*用 Redis **原子命令**解决；但**先判断再执行的组合动作**原子命令管不了，需要**加锁把整段变互斥**；

进程内的锁跨不了进程，所以**把锁挂在 Redis 上**，用 SET NX EX 实现——**NX 靠 Redis 单线程的原子性保证恰好一人抢到**，*EX 防止持有者宕机后锁永不释放*。我项目里用它防缓存击穿：热点 key 过期时只放一个请求回源重建，其余等待后读新值

## 客观法条回答缓存

缓存的是整个回答，省略掉整个agent链路，

在意图缓存之上，我又加了一层回答缓存。意图缓存只能省掉 Planner 一次判断，后面还得走完整检索和生成、仍有好几秒；回答缓存直接缓存客观知识问题的最终答案，命中就**跳过整条 Agent 链路——零 LLM 调用、秒回**。 最关键的是写入门控：只有**当这条消息无上下文、且 Planner 明确判定它是客观知识查询**时，我才缓存整条回答；个人案情咨询的答案绝不缓存，因为案情答案带个性化，缓存错发会误导别人——正确性优先于命中率。 key 做归一化 + sha256，和*意图缓存分前缀隔离，还带知识库版本号 v1*，**重建向量库后就改版本号，让旧答案自动失效**，避免法条更新后还回放旧答案。流式命中时我把缓存答案拆成 token 事件分段推给前端再补一个 done，前端无感。整层还是 fail-open，Redis 挂了自动降级走完整链路。


归一化＝把一句话抹平表面的花活：**去掉空格、标点、统一大小写**。这样"试用期最长多久？"和"试用期 最长 多久"就变成一模一样的写法，能认成同一个问题。（注意：只抹平标点空格这种皮，不认识同义词——"多久"和"多长时间"它还是当两个问题。）

sha256＝**把抹平后的这句话，变成一个固定长度的"条形码"**。同样的话→同样的码；不同的话→几乎不可能撞码；而且单向，从码倒推不回原话。

用条形码当 Redis 的 key（抽屉标签），答案放抽屉里。好处：标签短、统一、干净，再长再脏的问题都能变成一个规规矩矩的码。**归一化决定"哪些问题算同一个"，sha256 只是把它压成标签。**


### 修改版本号后，旧缓存去哪里了？

**旧缓存没被删，它还躺在 Redis 里，只是再也没人去读它了。**

原理在"钥匙"上：缓存的标签（key）里编进了版本号。

改版本前，读写都认 ...v1:问题码 这套标签。
改版本后，代码只算 ...v2:问题码 这套新标签——旧的那堆 v1 抽屉从此没人认领，变成"孤儿"。
这些孤儿不会被主动删除，而是各自等自己的 TTL 到期，被 Redis 自动扔掉。

所以分工是：

版本号＝"改主意"——我从此只用新标签（瞬间生效）。
TTL＝"收垃圾"——旧孤儿早晚自己过期消失。

**版本号只影响回答缓存和检索缓存（它们绑了向量库版本）；意图缓存不绑向量库版本**

## 对于缓存的总结

我给项目加了一套三层 Redis 缓存：

 ① `意图缓存`：缓存 Planner 的完整性判定，命中省一次 LLM 调用；只在 无上下文（**就是这句话的意思本身独立就可以存在不需要依赖上下文来确定**）首问生效，且判定 temperature=0 是确定的，同问同判、结果不含个人内容，所以适合缓存。

 ② `回答缓存`：缓存客观法条类问题的完整回答，*命中直接跳过整条 Agent 链路、省一整轮生成*。为保证正确性，只缓存"**无上下文 + Planner 判定为客观知识**"的问题，个人案情一律不缓存（防把个性化答案错发）。它命中率天然偏低，价值在省掉整条链路。
 
  ③ `检索缓存`：缓存检索产出的法条原文，*命中跳过最慢的重排序*；key 是归一化后相同的检索词（不是语义相似——语义会引错法条，故意没做）。实测平均每次命中省约 6 秒（跟机器重排速度相关）。
  
   整体：全层 fail-open，Redis 不可用自动降级、不拖垮回答；版本号做主动失效、TTL 兜底过期、*更新向量库时改版本号让旧缓存失效*；并加了命中率统计端点做可观测。 

   目的：主要是**降延迟、省 LLM 调用、减轻重排器 CPU 压力**；代价是多存一份数据、要管好失效与一致性。

**三层安全设计**：

① 意图层：你问"删除" → 直接拒绝+glm4.7进行意图识别的判断（还没生成 SQL，零成本，所以是可以优化的）
② SQL 校验层：生成的 SQL 必须 SELECT + 只能查白名单表 + 单条语句+ sqlglot（← 你说的"表白名单"在这层）
③ 数据库层：只读账号 → 就算前面漏了，数据库也会硬拒（1142）


1. 表白名单是因为MySQL自带几个系统库，
mysql.user —— 存所有数据库账号和加密后的密码！
information_schema.* —— 存所有库/表/字段的结构信息
performance_schema —— 存运行时性能数据

然后库里面存的是数据库自己的元数据，包括所有的数据库账号和加密后的密码。如果大模型没有办法去分清**业务表和系统表**的话，就会会泄露密码。所以白名单在SQL到达数据库之前，就拦住只允许碰指定的业务表

2. limit设计结果行数<200

a. SELECT * FROM messages防止大模型生成这种语句，把整个表都要查询一遍。这样会**拖垮数据库**,如果同时还有别的请求在跑这个库的话,就这一条查询会把*连接和io占满*

b. 此外会**占满上下文和内存**


3. sqlglot

sqlglot是SQL的语法解析器，把一条 SQL 字符串解析成语法树（AST），让你能在结构层面检查它，而不是在字符串层面瞎猜。功能有解析，语句计数。语句类型判断，表级白名单，危险函数拦截


SQL 安全校验我没用正则，而是用 sqlglot 把 SQL 解析成语法树再检查——因为正则只能抠字符串：FROM a, b 会漏掉第二张表、CTE 别名会被误判成越权表、子查询里的表根本看不见。

语法树能做到三件事：语句类型一票否决（非 SELECT 直接拒）、表级白名单（含子查询/UNION/CTE，带库名前缀也校验）、危险函数拦截（LOAD_FILE 读文件、SLEEP 延时拖库）。这三条能离线单测，零外部依赖。
